Test Case Generation Platform

A system that generates test plans and test cases from requirements, Jira context, and sanitized production logs. All data is stored in PostgreSQL, retrieval uses pgvector, and generation uses Vertex AI APIs only (Gemini + Embeddings).

Architecture

Minimal services: UI + API + Postgres + Vertex AI. Postgres stores both documents and outputs; pgvector powers retrieval.

Core components

  • React UI: trigger generation and display outputs + evidence.
  • Cloud Run API: ingestion, retrieval, orchestration, and job status.
  • Postgres + pgvector: documents, metadata, embeddings, traceability, outputs.
  • Vertex AI Embeddings: creates vectors for chunks and queries.
  • Vertex AI Gemini: generates test plan and test cases.
  • Validation Service: schema checks + rules + dedupe.
Constraint: Only Vertex AI APIs are allowed (Gemini + Embeddings). Storage must be Postgres (no GCS).

Outputs (what users get)

Test Plan JSON Test Cases XML/JSON Traceability links Evidence citations

Every generated item stores references to evidence chunks so reviewers can see why a test exists.

Where data lives (Postgres is the only storage)

All raw inputs, processed records, embeddings, and generated outputs are stored in Postgres. pgvector is used for similarity search.

Stored inputs

  • Jira snapshots (epics/stories/acceptance criteria)
  • Requirements documents (parsed text)
  • Sanitized production logs (patterns + error signatures)

Stored outputs

  • Generation jobs (status, timestamps, errors)
  • Test plans (JSON)
  • Test cases (XML/JSON)
  • Validation reports
  • Traceability links (requirement → test → evidence)

Key tables (logical)

  • datasets, documents (type, version, checksum)
  • knowledge_records (normalized records)
  • chunks (chunk text + metadata)
  • embeddings (vector column via pgvector)
  • generation_jobs, test_plans, test_cases, validation_reports
  • traceability_links (requirement_id → testcase_id → chunk_ids)

RAG approach (how the system “finds the right info”)

The platform first filters by metadata (country/flow/message type/capability) and then runs vector similarity on pgvector. This makes results more accurate and reduces hallucinations.

Normalize to “Knowledge Records”

  • REQ_STORY: story + acceptance criteria
  • JIRA_BEHAVIOR: implemented behavior + constraints
  • PROD_MESSAGE_PATTERN: canonical XML + variants
  • PROD_ERROR_PATTERN: error codes + triggers + expected handling
  • FIELD_RULE: validations, mappings, constraints

Multi-stage retrieval

  • Retrieve requirements + AC first
  • Then retrieve Jira constraints
  • Then retrieve prod templates and error patterns
  • Dedupe and build a token-budgeted context pack

Generation pipeline (safer 2-pass)

Pass A creates a structured test plan. Pass B generates final test cases from the plan. A non-LLM validator gates what is published.

Pass A — Test Plan

  • Gemini outputs structured JSON
  • Scenarios + mapping to requirements/AC
  • Coverage tags + open questions

Pass B — Test Cases

  • Generate XML/JSON test cases
  • Expected results + assertions
  • Traceability + evidence chunk ids

Pass C — Validation

  • XML schema (XSD)
  • Required fields + rules
  • Deduplication

API endpoints (minimal)

Simple endpoints for dataset creation, ingestion, generation, and result retrieval.

Security & guardrails

The system stores only sanitized data, keeps secrets out of code, and enforces structured outputs and validation rules.

Security basics

  • Service accounts for Vertex AI access
  • DB credentials stored securely (no hardcoding)
  • Sanitize logs before ingestion

LLM guardrails

  • Structured output (schema-constrained JSON)
  • Evidence-required generation (citations stored)
  • Low temperature for stable outputs

MVP build order

  • Postgres schema + dataset management
  • Requirements parsing → chunking → embeddings
  • pgvector retrieval + evidence display
  • Generate Test Plan (structured JSON)
  • Generate Test Cases + validators
  • Add Jira + production patterns
